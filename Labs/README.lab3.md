# Лабораторная работа №3

`GET /api/v1/labs/lab3/hours-report`

Обязательные параметры: `group_id` (UUID), `period_start`, `period_end` (YYYY-MM-DD).
Обе границы периода включены. Маршрут доступен через gateway с Bearer JWT.

## Выборка

1. PostgreSQL получает группу, её кафедру и специальность по `group_id`.
2. Neo4j собирает состав группы, затем отдельно занятия периода:
   `Group → Schedule → Lecture → Course`, `Student → Group`.
   Студенты агрегируются до обхода расписания; фильтр занятий — `type = 'Lecture'`.
3. PostgreSQL оставляет найденные курсы с `courses.department_id = groups.department_id`.
   Это признак специальной дисциплины кафедры. `technical_requirements` в фильтре не используется.
4. PostgreSQL считает уникальные посещённые занятия по студенту и курсу: `mark = 1`.
   В запрос передаются только пары `schedule_id/course_id` из выбранного графового среза,
   идентификаторы студентов и период. Условие по `attendance.date` отсекает ненужные партиции.
5. Redis возвращает JSON-профили по `student_id`. Отсутствующие профили получаются одним
   запросом PostgreSQL и сохраняются через pipeline `SETEX`, TTL — 86400 секунд.
   Формат ключей и значений совместим с лабой 1. При ошибке Redis используется PostgreSQL.
6. MongoDB возвращает институт и университет только для кафедры заданной группы.

## Часы и ответ

Ответ содержит `group`, период и `students`. У каждого студента находятся его поля и
`courses`: полные данные курса, `planned_classes`, `attended_classes`, `planned_hours`,
`attended_hours`. Плановые часы берутся из расписания группы, а не из общего поля
`course.lecture_hours` учебного плана. Одно занятие равно двум академическим часам.

Повторные отметки и повторные связи графа не увеличивают число занятий. При отсутствии
посещений возвращается 0. При пустом периоде группа и её студенты сохраняются,
но списки `courses` пусты. Неизвестная группа даёт 404, обратный период — 400,
неверный UUID или формат даты — 422; недоступность обязательного хранилища — 503.

## Запуск

Из каталога `Labs`:

```bash
../.venv/bin/uvicorn app_lab3:app --host 127.0.0.1 --port 8003
```

Для Compose добавлен `lab3-service` с `Dockerfile.lab3`; gateway использует
`LAB3_URL=http://lab3-service:8003`. Настройки подключений берутся из `Labs/.env`
и переменных окружения. Генератор и очистка данных для проверки лабы 3 не требуются.

Индекс начальной точки обхода Neo4j описан в `lab3_indexes.cypher`. Его нужно
применить при настройке базы и дождаться состояния ONLINE перед нагрузочными замерами.
PostgreSQL использует существующие ключи и индексы студентов и посещаемости.

## Проверки

Из корня проекта:

```bash
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -B -m unittest discover -s tests -p test_lab3.py
.venv/bin/python -B verify_lab3.py
```

Первый запуск проверяет пограничные случаи изолированно. Второй использует текущий
тестовый набор реальных БД: SQL-эталон независимо читает расписание PostgreSQL и
сравнивает полные HTTP-ответы для всех групп, полного периода, одного дня и пустого
периода. Проверяются Redis и HTTP-проксирование gateway. Данные БД не очищаются;
обычные записи кэша студентов в Redis могут создаваться и обновляться.

Это функциональная проверка на тестовом наборе, а не измерение нагрузки на миллиардах строк.
