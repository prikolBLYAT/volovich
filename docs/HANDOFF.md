## Лаба 1: что пользователь попросил и что исправлено

Требование: отчёт о студентах с минимальным процентом посещения лекций, в материалах которых есть заданный термин/фраза, за период. Полная информация о студенте, процент, период и термин.

Пользователь спросил, зачем после Elasticsearch выполнялся запрос в PostgreSQL для определения групп, и затем прямо попросил искать группы через Neo4j.

Текущая логика `../Labs/lab1.py`:

1. Elasticsearch ищет по `title^3` и `content_text` в индексе **`course_materials`**, получает уникальные `lecture_id`.
2. Neo4j находит группы по фактическому расписанию найденных лекций, затем студентов:
   `Lecture <-[:FOR_LECTURE]- Schedule <-[:HAS_SCHEDULE]- Group <-[:BELONGS_TO]- Student`.
   Фильтры: даты включительно, найденные lecture IDs, `l.type = 'Lecture'`.
3. PostgreSQL считает уникальные посещённые занятия (`mark = 1`) по выбранным schedule/student IDs и периоду.
4. Студенты фильтруются по диапазону процента, сортируются по проценту возрастанию, числу занятий убыванию, затем student ID; применяется limit.
5. PostgreSQL получает атрибуты **только групп итогового списка**.
6. Redis возвращает JSON-карточки студентов по `student_id`; промахи читаются одним SQL-запросом и сохраняются с TTL 86400 секунд. Ошибки Redis допускают fallback к PostgreSQL.
7. MongoDB возвращает иерархию кафедра/институт/университет.
8. При сборке ответа группа берётся из графового расчёта (`stats['group_id']`), а не из потенциально устаревшего group_id в карточке Redis.

Предварительный SQL-поиск групп удалён. Если Elasticsearch или Neo4j не нашли нужных данных, PostgreSQL не вызывается.
Для непустого отчёта с прогретыми карточками Redis остаются два PG-подключения: посещения и метаданные групп.

**Семантика:** принадлежность группы занятию теперь определяется графовой связью расписания. Отдельный предварительный SQL-фильтр по специальности и кафедре курса/группы больше не выполняется.
Генератор создаёт расписание в рамках соответствующей пары кафедра/специальность. При некорректных межкафедральных связях результат может отличаться от старого алгоритма. Это было сообщено пользователю. Полей кафедры/специальности на узлах Group/Course для такой проверки в Neo4j на момент анализа не было.

## Лаба 2: смысл отчёта и исправление нулевых лекций

Текст требования: отчёт о необходимом объёме аудитории для занятий по курсу заданного семестра и года обучения с требованиями к техническим средствам; результат должен содержать полную информацию о курсе, лекции и количестве слушателей.

Текущий API использует `semester` и **`enrollment_year` как год поступления группы**. Сохранить это поведение, если пользователь отдельно не уточнит другой смысл «года обучения».

Текущая логика `../Labs/lab2.py`:

1. PostgreSQL выбирает курсы нужного семестра и лекции `type='Lecture'`, `technical_requirements IS TRUE`, а также атрибуты курса и специальности.
2. Neo4j находит расписание этих лекций и группы нужного года набора. `count(DISTINCT sc)` вычисляется на уровне курса/лекции/группы **до** обхода студентов.
3. Обязательный `MATCH (st:Student)-[:BELONGS_TO]->(g)` исключает группы без студентов; число слушателей группы считается как `count(DISTINCT st)`.
4. Для лекции: число занятий суммируется по группам, слушатели суммируются по уникальным группам, вместимость равна максимальному размеру одной группы.
5. Для курса: размер каждой группы учитывается один раз даже при нескольких лекциях этой группы.
6. PostgreSQL получает кафедру/институт/ID университета только нужных курсов; MongoDB — названия нужных университетов.
7. В ответ попадают **только лекции, найденные в графовой выборке, с положительным числом занятий и слушателей**. Курсы с пустым итоговым списком лекций исключаются.

Инвариант подсчёта: студент принадлежит одной группе. Не менять дедупликацию на простое число путей Student × Schedule.

### Где находится полная информация в ответе

Ответ — JSON-массив курсов; вложенный `lectures` содержит лекции.

Поля курса (`CourseAudienceReportDTO`):

```text
course_id, course_name, description, semester, enrollment_year,
speciality_id, speciality_name, speciality_code,
department_id, department_name, institute_name,
university_id, university_name,
duration_hours, lecture_hours, practice_hours,
total_enrolled_students, lectures
```

Поля лекции (`LectureAudienceInfoDTO`):

```text
lecture_id, lecture_title, annotation, lecture_type,
technical_requirements, scheduled_classes_count,
total_listeners_count, required_room_capacity
```

`total_listeners_count` — уникальные слушатели лекции в выбранном срезе групп; `total_enrolled_students` — слушатели курса без повторного учёта группы; `required_room_capacity` — максимум численности одной группы в текущей реализации.
Число слушателей выводится по составу групп, не по отметкам фактической посещаемости.

## Лаба 3: имеющийся код, не основная задача этой беседы

Текущая логика по прочитанному коду:

1. PG получает группу, кафедру и специальность; неизвестная группа — 404, неверный порядок дат — 400.

4. PG считает посещённые уникальные занятия по студенту/курсу в выбранном графовом срезе, `mark=1`.
5. Redis возвращает карточки студентов, промахи — одним PG-запросом; запись через pipeline, TTL сутки. При несовпадении состава/отсутствии карточки возвращается 503.
6. MongoDB обогащает группу иерархией.
7. Одно занятие = 2 академических часа. В отчёте сохраняются студенты с нулевой посещаемостью и студенты без занятий за период.

## Модель данных и конфигурация

PostgreSQL:

- `universities -> institutes -> departments`;
- `specialities`, `department_specialties`;
- `groups(speciality_id, department_id, enrollment_year, ...)`;
- `students(group_id, ..., student_card_number, status)`;
- `courses(speciality_id, department_id, semester, duration_hours, lecture_hours, practice_hours, ...)`;
- `lectures(course_id, title, technical_requirements BOOLEAN, annotation, type)`;
- `schedule(class_id -> lectures.id, group_id, schedule_date, period, ...)`;
- `attendance(schedule_id, student_id, date, period, mark, ...)`, партиционирование по неделям.

Neo4j:

```text
(Student)-[:BELONGS_TO]->(Group)
(Group)-[:HAS_SCHEDULE]->(Schedule)
(Schedule)-[:FOR_LECTURE]->(Lecture)
(Lecture)-[:OF_COURSE]->(Course)
```

IDs хранятся строками UUID; `Group.enrollment_year` генерируется целым числом; `Schedule.date` — строка ISO date; `Lecture.type` присутствует.
`Course.semester` и `Lecture.technical_requirements` для лабы 2 отбираются в PG, не требуют дублирования в графе.

MongoDB: коллекция `university_hierarchy`, документы университетов с `university_id`, `name`, вложенными `institutes` и `departments`.

Elasticsearch: индекс `course_materials`, поля `lecture_id`, `course_id`, `material_id`, `title`, `content_text` и др.; русский анализатор. Несколько материалов могут относиться к одной лекции, поэтому lecture IDs дедуплицируются.

Redis: карточки студентов с JSON-полями student_id, group_id, first_name, second_name, email, phone, student_card_number, status; ключ — строковый student_id в текущих лабах 1 и 3.

В корне и `../Labs` существуют `.env`. Их содержимое сюда не копировать.
`lab1.py` ищет корневой `.env`; `lab2.py`, `lab3.py`, gateway — `Labs/.env` при локальном запуске. В контейнерах Compose передаёт окружение через env_file. Проверять источники настроек при диагностике.
