# Диаграммы лабораторных работ №1–3

Диаграммы описывают **текущую реализацию**, а не желаемую архитектуру. Формат — Mermaid `.mmd`, русские подписи, стандартная светлая тема. C4 — уровни Context, Container, Component со стереотипами и границами на Mermaid `flowchart`, **не уровень Code**. Нативный C4-рендерер заменён после визуальной проверки: он накладывал подписи на узлы; содержание и уровни модели сохранены. DFD — `flowchart`, но с семантикой потоков данных Йордана—Кода, не блок-схема управления.

## Границы и уровни C4

- **C1:** один реальный внешний актор — аналитик / HTTP-клиент. Граница системы охватывает общий API Gateway, отдельные сервисы ЛР 1–3 и используемые ими хранилища. Сценарий каждой работы — срез **одной системы**, а не три независимых gateway. UI, внешний Identity Provider, отдельный сервис авторизации или администратор-загрузчик не выдуманы: их в рассматриваемых сценариях нет. Хранилища не представлены внешними бизнес-акторами.
- **C2:** общий `api-gateway` и конкретный `labN-service`, плюс только реально используемые этим сервисом хранилища. Другие лабораторные сервисы опущены как соседние срезы. Базы данных логически входят в систему, но **не разворачиваются** в `Labs/docker-compose.yaml`; их адреса берутся из окружения. Граница C4 не означает отдельную сеть, доверенную зону или одну Compose-конфигурацию.
- **C3:** две подписанные границы контейнеров показывают компоненты gateway и выбранного сервиса. Это компонентные срезы, не диаграмма классов: используются имена реальных handlers, helpers и DTO. «Расчёт и обогащение» — явно **логические участки монолитного handler**, не существующий отдельный класс, сервис или сетевой вызов. DTO — реальные схемы Pydantic. Внешние контейнеры-хранилища уже раскрыты на C2; их data flows подробно показаны в DFD. В C3 нет выдуманного repository/service-слоя.
- Lab1 использует PostgreSQL, Neo4j, MongoDB, Redis, Elasticsearch. **Lab2 использует только PostgreSQL, Neo4j, MongoDB: Redis и Elasticsearch отсутствуют. Lab3 не использует Elasticsearch.**

## Легенда DFD Йордана—Кода

- `E1` — прямоугольная внешняя сущность: клиент, находящийся вне рассматриваемой системы или декомпозируемого процесса.
- Круг `((...))` — процесс преобразования данных. `1.0` агрегирует локальный login, проверку JWT и HTTP proxy gateway; `2.0` агрегирует handler сервиса. В detail `2.1`–`2.3` раскрывают процесс `2.0`. Это не отдельные deployable-компоненты.
- `D1`–`D5` — хранилища. Mermaid `lined-rectangle` — **приближение открытого хранилища Йордана—Кода**: дополнительная линия обозначает хранилище, но форма не воспроизводит буквально две открытые параллельные линии. Круги процессов и прямоугольники сущностей остаются различимы без цвета.
- Каждая стрелка направлена и подписана **содержимым данных**, включая запросы к хранилищам и возвращаемые наборы. Нет ромбов решений, ветвей «да/нет» или control-flow-связей. Порядок исполнения, ветвления и обработка исключений пояснены ниже, а не выданы за DFD.
- На overview отдельны login → JWT и запрос отчёта с Bearer JWT. В gateway проверяются подпись и `exp`; только после успешной проверки запрос передаётся сервису. Конфигурация credentials и JWT secret приходит из окружения; это не база пользователей и не отдельный Identity Provider. Значения секретов не документируются.
- Стрелка прямого вызова с published-порта показывает отдельный вход без JWT; ответ также явно направлен клиенту. В detail gateway/прямой клиент — внешняя сущность **относительно процесса 2.0**, а не утверждение о внешнем gateway на уровне всей системы.
- UUID на запросе MGET и UUID→JSON на SETEX — именно data flows чтения/записи кэша, не кэш готового отчёта. PostgreSQL fallback явно указан в overview и detail.
- Схемы насыщены именованными потоками; декомпозиции lab1/3 выделены отдельно. Это сознательное исключение из малого бюджета стрелок дизайнерского шаблона: удаление обратных потоков или fallback исказило бы DFD. Размер выбирает Mermaid автоматически; SVG/HTML-геометрия и шаблон pipeline из skill здесь не используются по требованию Mermaid и нотации Йордана—Кода.

## Контракт и семантика API

Общий вход: `http://<host>:8000`. Login: `POST /api/v1/auth/login`, OAuth2 form `username`, `password`. Ответ: `access_token`, `token_type=bearer`. JWT HS256 содержит `sub`, `role=analyst`, `exp`; срок — **12 часов**. Поле `role` выпускается, но отдельная проверка роли в `verify_jwt` не реализована. Gateway передаёт исходные query и Authorization через httpx, timeout **30 секунд**; неуспешный ответ сервиса оборачивается в HTTPException, поэтому форма ошибки через gateway может отличаться от прямой.

### Lab1 — `GET /api/v1/labs/lab1/attendance-report`

- Обязательные `term`, `period_start`, `period_end`; даты включительно. `min_attendance_pct=0`, `max_attendance_pct=100`, обе границы 0–100; `limit=10`, диапазон 1–100. Обратный период или диапазон процентов → 400; ошибки типов/ограничений FastAPI → 422.
- Elasticsearch `course_materials`: `multi_match` по `title^3` и `content_text`, **до 10000 hits**, не `match_phrase` и не бесконечная пагинация. Уникальные `lecture_id` передаются Neo4j.
- Neo4j ограничивает расписания периодом и `Lecture.type='Lecture'`, возвращает группы, студентов и уникальные занятия. Знаменатель процента — число выбранных `schedule_id` **группы студента**, не число всех найденных материалов.
- PostgreSQL считает `COUNT(DISTINCT schedule_id)` с `mark=1`, датой в периоде и согласованностью группы студента с расписанием. Пропущенная строка статистики означает ноль посещений. Процент округляется до двух знаков, затем фильтруется. Сортировка: процент ASC, число занятий DESC, UUID ASC; затем `limit`.
- Только итоговые группы обогащаются из PostgreSQL, итоговые студенты — из Redis/PG, кафедры — из MongoDB. Нет подходящих лекций/студентов → пустой корректный отчёт. `matching_lectures_count` после Neo4j — число уникальных лекций с расписаниями в области студентов, не число hits ES.
- Ответ `ReportResponseDTO` содержит параметры периода/термина/процентов, число лекций и полные профили со статистикой. `limit` сам по себе полем ответа не является. Нет fallback ES/Neo4j/MongoDB: ошибки не заменяются фиктивными результатами.

### Lab2 — `GET /api/v1/labs/lab2/audience-report`

- Обязательные `semester` и `enrollment_year`, целые ≥1. **`enrollment_year` — календарный год набора группы, не номер курса обучения.**
- PostgreSQL отбирает курсы по семестру и только `Lecture` с `technical_requirements IS TRUE`. Это boolean в строке лекции, **не полнотекстовый поиск технических требований** и не подбор конкретной аудитории.
- Neo4j выбирает группы нужного набора, имеющие расписания выбранных лекций и студентов. `scheduled_classes_count` суммирует уникальные занятия по группам; `total_listeners_count` суммирует число студентов групп, **не умножая на число повторных занятий**.
- **`required_room_capacity` — максимум размера одной участвующей группы для конкретной лекции**, не сумма слушателей всех групп и не одновременная потребность нескольких потоков. Допущение кода — студент принадлежит одной группе; общий `total_enrolled_students` курса складывается по уникальным группам.
- Кафедра, институт и UUID вуза берутся из PostgreSQL; MongoDB возвращает названия только нужных вузов. Лекции без занятий или слушателей исключаются; отсутствие данных → `[]`. Ответ — список `CourseAudienceReportDTO` с `LectureAudienceInfoDTO`.
- Redis, кэш отчёта и Elasticsearch отсутствуют и в реализации, и в диаграммах. Эта работа не вычисляет посещаемость по attendance.

### Lab3 — `GET /api/v1/labs/lab3/hours-report`

- Обязательные `group_id` (UUID), `period_start`, `period_end` (даты включительно). Неверный UUID → 422, обратный период → 400, нет группы в PostgreSQL → 404.
- PostgreSQL возвращает группу, специальность, кафедру. Neo4j получает состав группы и уникальные `schedule_id` по курсам только для `Lecture` в периоде. Сначала агрегируются студенты, затем занятия: декартово размножение Student × Schedule исключено.
- **«Специальная дисциплина кафедры» в коде означает `courses.department_id == group.department_id`**, не отдельный тег, не `technical_requirements`, не равенство специальностей. Курсы без выбранных лекционных занятий в периоде не добавляются.
- PostgreSQL считает посещения `mark=1` по точным парам schedule–course и студентам. **Одна запланированная или посещённая лекция равна двум академическим часам**: `planned_hours = planned_classes × 2`, `attended_hours = attended_classes × 2`. Это расчёт из расписания/посещений, а не копирование `courses.lecture_hours`.
- Redis/PG дают профили всех студентов группы, MongoDB — институт и вуз кафедры. Нет группы в Neo4j или состав PG не совпадает с отсутствующими в кэше UUID → 503. При отсутствии выбранных курсов студенты могут присутствовать с пустыми `courses`.
- Ответ `GroupHoursReportDTO`: группа, период, `academic_hours_per_lecture=2`, студенты и курсы с планом и фактом. Elasticsearch отсутствует.

## Общий кэш профилей lab1/3

Ключ — **строковый UUID студента**, значение — JSON профиля; `SETEX(..., 86400, ...)`, **сутки**. Это не номер зачётной книжки и не ключ параметров отчёта. Зачётная книжка — поле профиля. Это отличие от описания Redis в практической части `Задание.docx`; диаграммы фиксируют текущий код лабораторных работ.

`MGET` → проверка JSON/обязательных полей → отсутствующие или невалидные профили читаются пакетом из PostgreSQL → записываются в Redis. Недоступность Redis не должна ломать отчёт: используется PG fallback, ошибки записи кэша подавляются/логируются. Lab1 проверяет набор обязательных полей, **но не сверяет UUID/группу так строго, как lab3**; lab3 также проверяет совпадение `student_id` и `group_id`, требует согласованность полученного состава. В lab3 SETEX отправляются через pipeline без транзакции. Автоматической инвалидации при изменении профиля нет: данные могут устареть до истечения TTL.

## Безопасность и развёртывание

JWT проверяется **только в gateway**. Сервисы получают Authorization, но не валидируют его. `Labs/docker-compose.yaml` публикует `8000:8000`, **`8001:8001`, `8002:8002`, `8003:8003`** без ограничения host IP, поэтому доступный извне lab-порт позволяет обойти аутентификацию шлюза. Фактическая доступность зависит от firewall/хоста; её здесь не проверяли. Диаграмма не утверждает, что обход заблокирован.

В текущем Compose и коде используются HTTP, а не настроенный TLS/HTTPS. Отдельного authorization/RBAC, внешнего OAuth-провайдера и секретного vault в рассматриваемом коде нет. Никакие реальные credentials или значения переменных окружения в документацию не переносились.
