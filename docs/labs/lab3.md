# Лабораторная работа №3: часы лекций по всем группам

Разбор текущих [`get_hours_report`](../../Labs/lab3.py) и [`get_student_profiles`](../../Labs/lab3.py), а также прокси в [`gateway.py`](../../Labs/gateway.py).

**Входного `group_id` нет.** Метод принимает даты и необязательный `group_name`: точное название группы с учётом регистра. Без него возвращается массив отчётов по всем группам; с ним — по совпавшим группам. Если названия повторяются, возвращаются все совпадения. Форма ответа всегда массив. UUID групп остаются в результатах и внутренних запросах, потому что без них нельзя связать студентов, расписание и кафедры.

## 1. Что считается

Общие сведения о курсах и план группы находятся в `courses` на уровне отчёта группы. У каждого студента в `attendance` остаются только `course_id` и индивидуальные показатели посещения. Показатели разделены так:

- `planned_classes` — число уникальных запланированных занятий группы за период;
- `attended_classes` — число этих занятий, которые студент посетил;
- `planned_hours` — число плановых занятий, умноженное на 2;
- `attended_hours` — число посещённых занятий, умноженное на 2.

В расчёт входят только занятия типа `Lecture` и курсы кафедры группы. Отдельный текстовый тег специальной дисциплины код не ищет: его смысл в этой схеме заменён условием совпадения кафедр.

Путь данных:

```text
Gateway: JWT, даты и необязательное название группы
  → Neo4j: выбор групп по названию, состав и занятия за период
  → PostgreSQL: данные выбранных групп и специальностей
  → Python: точные пары course_id / department_id
  → PostgreSQL: подходящие курсы
  → Python: точные тройки schedule_id / course_id / group_id
  → PostgreSQL: агрегаты посещений
  → Redis: профили всех студентов одним MGET
      → PostgreSQL: все промахи по точным парам student_id / group_id
      → Redis: один pipeline записи профилей
  → MongoDB: иерархия кафедр всех групп одним find
  → Python: часы и JSON-массив отчётов по группам
```

Elasticsearch не используется: здесь нет поиска по текстовым материалам. Запросы не запускаются параллельно, но область каждой БД читается пакетно, без отдельной цепочки запросов на каждую группу.

## 2. Входные параметры и Gateway

```http
GET /api/v1/labs/lab3/hours-report?period_start=2026-09-01&period_end=2026-12-31
Authorization: Bearer <JWT>
```

| Параметр | Значение по умолчанию в Gateway | Смысл |
|---|---|---|
| `period_start` | `2026-09-01` | Начало периода включительно |
| `period_end` | `2026-09-30` | Конец периода включительно |
| `group_name` | Не задано | Точное название; без параметра — все группы |

Для всего осеннего расписания конец декабря указывается явно. Без параметров Gateway запрашивает сентябрь, а не весь сформированный генератором период.

Шлюз проверяет подпись JWT HS256 и срок штатного токена. Метод входа сравнивает логин/пароль с настройками окружения без обращения к БД и выдаёт токен на 12 часов с `sub`, `role='analyst'`, `exp`. Отдельной проверки роли в прокси нет.

Прокси отправляет GET в `LAB3_URL`, по умолчанию `http://lab3-service:8003`, на тот же путь. Для третьей лабы он передаёт даты и добавляет название группы, только если оно задано:

```python
params={
    'period_start': period_start,
    'period_end': period_end,
}
if group_name is not None:
    params['group_name'] = group_name
```

Поэтому старый `group_id`, даже если вручную приписать его к URL Gateway, не передаётся сервису и не ограничивает отчёт. В OpenAPI он также отсутствует. Неизвестный параметр сам по себе не вызывает отказ FastAPI, но фильтром от этого не становится.

Gateway передаёт `Authorization` и ждёт сервис через HTTP-клиент с тайм-аутом 30 секунд. Сам Gateway БД не читает.

В сервисе даты обязательны и преобразуются в `date`. Если дата не разбирается — 422. Если `period_start > period_end` — 400 до запросов к БД. Значения по умолчанию существуют в Gateway; в самом сервисе даты объявлены как `Query(...)`.

## 3. Запрос №1. Neo4j: состав и расписание всех групп

```cypher
MATCH (g:Group)
OPTIONAL MATCH (st:Student)-[:BELONGS_TO]->(g)
WITH g, collect(DISTINCT st.id) AS student_ids
OPTIONAL MATCH (g)-[:HAS_SCHEDULE]->(sc:Schedule)
               -[:FOR_LECTURE]->(l:Lecture)-[:OF_COURSE]->(c:Course)
WHERE sc.date >= $period_start AND sc.date <= $period_end
  AND l.type = 'Lecture'
WITH g, student_ids, c.id AS course_id, collect(DISTINCT sc.id) AS schedule_ids
RETURN g.id AS group_id, student_ids,
       collect(CASE WHEN course_id IS NULL THEN null
       ELSE {course_id: course_id, schedule_ids: schedule_ids} END) AS courses
```

### Параметры

```python
period_start = str(period_start)
period_end = str(period_end)
```

Графовая структура:

```text
Student ─BELONGS_TO→ Group
Group ─HAS_SCHEDULE→ Schedule ─FOR_LECTURE→ Lecture ─OF_COURSE→ Course
```

### Как устроен запрос

1. `MATCH (g:Group)` выбирает группы. При заданном имени сразу после MATCH добавляется `WHERE g.name = $group_name`; имя передаётся отдельным параметром, с точным сравнением и без обрезания значимых пробелов. Без имени условия по названию нет. Это первый запрос к БД. Пустой результат даёт `[]` без фильтра либо 404 с именем — без PostgreSQL, Redis и MongoDB.
2. `OPTIONAL MATCH` студентов сохраняет группу даже без состава.
3. `WITH g, collect(DISTINCT st.id)` сворачивает студентов до обхода расписания. Так состав не умножает число строк занятий.
4. Второй `OPTIONAL MATCH` ищет расписание, лекцию и курс.
5. `sc.date >= ... AND sc.date <= ...` ограничивает период; `l.type = 'Lecture'` убирает практики и лабораторные.
6. Для каждой пары группы и курса собираются уникальные `schedule_ids`.
7. Возвращается одна строка на группу со списком студентов и вложенным списком курсов.

`WHERE` при втором `OPTIONAL MATCH` относится к поиску этого необязательного шаблона. Если занятий за период нет, группа не теряется. Для отсутствующего курса `CASE` даёт `null`, который не накапливается как полноценный объект курса.

Строковые даты `Schedule.date` сравниваются корректно при согласованном формате `YYYY-MM-DD`.

### Поля результата

```text
group_id
student_ids[]
courses[]
  course_id
  schedule_ids[]
```

Группы с пустым составом имеют `student_ids=[]`. Группы без лекционных занятий за период имеют `courses=[]`.

### Проверки после Neo4j

- Полученные UUID сортируются и передаются в PG одним массивом; отсутствие обязательных групп в PG даёт 503. Группы, отсутствующие в графе, отдельно не ищутся в PG.
- UUID студентов каждой группы дополнительно дедуплицируются и сортируются в Python.
- Списки занятий каждого курса также дедуплицируются и сортируются.
- Если один UUID студента попал в разные группы, возвращается 503.

Создаются структуры:

```python
students_by_group[group_id] = [student_id, ...]
schedules_by_group[group_id][course_id] = [schedule_id, ...]
student_groups[student_id] = group_id
```

`student_groups` затем сортируется по UUID студента. Это задаёт стабильный порядок общего MGET и его сопоставления с ответами.

**Проверка состава не полная в обе стороны:** граф задаёт студентов отчёта. Если студент есть в PG, но вообще не включён в графовый состав, отдельного сравнения всех студентов PG с графом здесь нет. Проверки профилей ниже выполняются для UUID, которые граф уже вернул.

## 4. Запрос №2. PostgreSQL: группы и специальности

```sql
SELECT g.id AS group_id, g.name AS group_name, g.speciality_id, g.department_id,
       g.enrollment_year, g.curator, sp.name AS speciality_name,
       sp.code AS speciality_code, sp.degree_level, sp.duration
FROM groups g
JOIN specialities sp ON sp.id = g.speciality_id
WHERE g.id = ANY(%s::uuid[])
ORDER BY g.id;
```

Этот SQL выполняется **после Neo4j**, на том же PG-подключении, что запросы курсов и посещений. Параметры: `(group_ids,)`, где UUID получены из графа. Фильтр названия выполняется в Neo4j, а не повторяется в PostgreSQL.

### Откуда берутся поля

| Поле | Таблица/смысл |
|---|---|
| `group_id` | `groups.id`, UUID группы |
| `group_name` | `groups.name` |
| `speciality_id` | UUID специальности группы |
| `department_id` | UUID кафедры группы для фильтра курсов и MongoDB |
| `enrollment_year` | Год поступления группы |
| `curator` | Куратор |
| `speciality_name`, `speciality_code` | Название и код из `specialities` |
| `degree_level`, `duration` | Уровень образования и длительность программы из `specialities` |

Группы сортируются по UUID `g.id`, не по названию. Внутренний JOIN предполагает корректную связь `groups.speciality_id → specialities.id`: без соответствующей специальности группа не появится в выборке.

Python создаёт `groups[group_id] = GroupInfoDTO(...)`. UUID становятся строками, названия подразделений пока не заполнены: они появятся из MongoDB.

Если множество UUID из PG отличается от полученного из графа, возвращается 503: обязательные данные группы отсутствуют. Полной проверки групп, существующих только в PG, здесь нет: область отчёта теперь задаётся Neo4j.

## 5. Подготовка точных пар курса и кафедры

Для каждой группы известны её `department_id` из PG и `course_id` из графового расписания. Формируется множество:

```python
candidate_pairs = sorted({
    (course_id, groups[group_id].department_id)
    for group_id, course_map in schedules_by_group.items()
    for course_id in course_map
})
```

Пары удаляют повторы, но сохраняют соответствие курса кафедре.

Это важнее двух независимых списков `course_id IN (...)` и `department_id IN (...)`: независимые списки допустили бы сочетания, которых не было в исходных парах. Здесь соответствие передаётся явно.

Если пар нет, SQL курсов и SQL посещений пропускаются. Состав студентов при этом остаётся нужным для отчёта.

## 6. Запрос №3. PostgreSQL: курсы нужных кафедр

```sql
SELECT id AS course_id, speciality_id, department_id, name AS course_name,
       description, semester, duration_hours, lecture_hours, practice_hours
FROM courses
WHERE (id, department_id) IN (
    SELECT * FROM unnest(%s::uuid[], %s::uuid[])
)
ORDER BY semester, name, id;
```

### Параметры по порядку

```python
(
    [pair[0] for pair in candidate_pairs],  # course_id
    [pair[1] for pair in candidate_pairs],  # department_id
)
```

Два массива имеют одинаковую длину и собираются из одного списка пар.

### Как работает `unnest`

```sql
SELECT * FROM unnest(%s::uuid[], %s::uuid[])
```

Многомассивный `unnest` раскрывает значения **по одинаковым позициям**, а не делает декартово произведение массивов. Первая колонка содержит UUID курса, вторая — соответствующий UUID кафедры. Кортеж `(id, department_id) IN (...)` требует точного совпадения пары.

### Поля результата

| Поле | Смысл |
|---|---|
| `course_id` | UUID курса |
| `speciality_id` | UUID специальности курса |
| `department_id` | UUID его кафедры |
| `course_name`, `description` | Название и описание |
| `semester` | Семестр курса |
| `duration_hours`, `lecture_hours`, `practice_hours` | Учебный объём курса из каталога |

Сортировка выполняется по `semester, name, id`.

**Не фильтруются** `speciality_id` группы/курса и `technical_requirements`: специальность курса может отличаться от специальности группы, а требование оборудования не определяет специальную дисциплину в этой лабе. Критерий — кафедра.

### Повторная привязка к конкретной группе

Один курс может подходить нескольким группам. Из общего результата PG Python для каждой группы оставляет строки, одновременно удовлетворяющие:

```python
str(row['department_id']) == group.department_id
and str(row['course_id']) in schedules_by_group[group_id]
```

Так появляются `courses_by_group[group_id]`. Одного попадания курса в общую PG-выборку недостаточно, чтобы добавить его во все группы.

Цикл по группам здесь выполняется в памяти. Он не запускает новые SQL-запросы.

## 7. Подготовка троек расписания

Из окончательных курсов каждой группы берутся её графовые занятия:

```text
selected_scope = [
  (schedule_id, course_id, group_id),
  ...
]
```

Тройка хранит принадлежность конкретного занятия конкретному курсу и группе. Отдельные независимые множества этих UUID потеряли бы такое соответствие.

Если `selected_scope` пуст или не найден ни один студент, SQL посещений не выполняется.

## 8. Запрос №4. PostgreSQL: посещения всех групп

```sql
WITH selected_schedule AS (
    SELECT * FROM unnest(%s::uuid[], %s::uuid[], %s::uuid[])
        AS scope(schedule_id, course_id, group_id)
)
SELECT sc.group_id, a.student_id, sc.course_id,
       COUNT(DISTINCT a.schedule_id) AS attended_classes
FROM selected_schedule sc
JOIN attendance a ON a.schedule_id = sc.schedule_id
JOIN students st ON st.id = a.student_id AND st.group_id = sc.group_id
WHERE a.student_id = ANY(%s::uuid[])
  AND a.date BETWEEN %s AND %s AND a.mark = 1
GROUP BY sc.group_id, a.student_id, sc.course_id;
```

### Параметры по порядку

```python
(
    [item[0] for item in selected_scope],  # schedule_id
    [item[1] for item in selected_scope],  # course_id
    [item[2] for item in selected_scope],  # group_id
    list(student_groups),                # все UUID студентов графа
    period_start,
    period_end,
)
```

### Что делает запрос

1. CTE `selected_schedule` раскрывает три массива по одинаковым позициям в строки с колонками `schedule_id, course_id, group_id`.
2. `JOIN attendance` выбирает отметки точных занятий из этой области.
3. `JOIN students` проверяет, что студент отметки принадлежит той же группе в PG.
4. `a.student_id = ANY(...)` ограничивает отметки студентами графовой выборки.
5. `a.date BETWEEN ...` проверяет даты отметок; это также условие по ключу месячных партиций `attendance`.
6. `a.mark = 1` оставляет присутствия.
7. `GROUP BY` считает результат по группе, студенту и курсу.

### Поля результата

```text
group_id
student_id
course_id
attended_classes
```

`COUNT(DISTINCT a.schedule_id)` считает каждое посещённое занятие один раз. Повторные отметки одного расписания не добавляют часы повторно.

В памяти результат имеет ключ из трёх UUID:

```python
attendance[(group_id, student_id, course_id)] = attended_classes
```

Для отсутствующей строки позднее подставляется ноль. Отсутствие присутствий не удаляет студента.

### Где проходит граница доверия

Связь расписания с курсом и группой в `selected_scope` пришла из Neo4j. Этот SQL не соединяется с таблицей `schedule`, чтобы заново доказать все эти связи и дату расписания в PG. Он проверяет группу студента и дату отметки. Поэтому согласованность UUID, графовых связей и дат между СУБД остаётся обязательным условием.

## 9. Запрос №5. Redis: все профили одним MGET

Вызывается `get_student_profiles(student_groups)`, где аргумент — словарь `student_id → ожидаемый group_id` из графа.

Если словарь пуст, функция возвращает `{}` без Redis и PostgreSQL.

Иначе:

```python
student_ids = list(student_groups)
raw_profiles = redis_client.mget(student_ids)
```

Ключи — сырые UUID студентов без префиксов. MGET возвращает значения в порядке ключей.

### Когда кэш принимается

JSON должен разбираться в словарь и содержать поля:

```text
student_id, group_id, first_name, second_name,
email, phone, student_card_number, status
```

Дополнительно проверяется:

```python
profile['student_id'] == requested_student_id
profile['group_id'] == student_groups[requested_student_id]
```

Невалидный JSON, отсутствие обязательного ключа, неверный UUID студента или другая группа делают запись промахом. Отсутствующий ключ Redis также считается промахом. Ошибка Redis не отменяет отчёт: все отсутствующие профили читаются из PG.

Почта, телефон и статус могут быть `null` в модели ответа, но ключи в JSON всё равно должны присутствовать. Наличие ключей и совпадение UUID — это не полная проверка всех типов и бизнес-значений кэшированного объекта.

При корректном попадании кэша новое чтение этого профиля из PG не выполняется. Поэтому эта проверка сама по себе не доказывает, что PG не изменился после заполнения кэша.

## 10. Условный запрос №6. PostgreSQL: промахи профилей

```sql
SELECT id AS student_id, group_id, first_name, second_name,
       email, phone, student_card_number, status
FROM students
WHERE (id, group_id) IN (
    SELECT * FROM unnest(%s::uuid[], %s::uuid[])
);
```

### Параметры

```python
(
    missing_ids,
    [student_groups[sid] for sid in missing_ids],
)
```

Массивы передают точные пары `student_id, group_id`. Это не «найти любого студента с подходящим UUID или любой подходящей группой», а совпадение обеих частей пары.

### Возвращаемые поля

```text
student_id, group_id, first_name, second_name,
email, phone, student_card_number, status
```

Все промахи всех групп обрабатываются одним запросом. Затем UUID приводятся к строкам.

### Проверка полноты

- множество полученных UUID должно точно совпасть с `missing_ids`;
- группа каждого профиля должна совпасть с ожидаемой группой из `student_groups`.

При нарушении — 503 «Состав группы в PostgreSQL и Neo4j не согласован». В отличие от первой лабы, отсутствие обязательного профиля не приводит к тихому пропуску студента.

Проверка относится к запрошенным промахам; она не сравнивает полные реестры всех студентов двух СУБД.

## 11. Условная запись №7. Redis: pipeline

```python
with redis_client.pipeline(transaction=False) as pipeline:
    for student_id, profile in fetched.items():
        pipeline.setex(
            student_id,
            86400,
            json.dumps(profile, ensure_ascii=False),
        )
    pipeline.execute()
```

В pipeline по-прежнему находится отдельная команда `SETEX` для каждого полученного профиля, но они отправляются одним пакетом. Это не один общий ключ и не SQL-транзакция.

`transaction=False` означает, что pipeline не оборачивается в Redis `MULTI/EXEC`. Он используется для пакетной доставки команд, а не для атомарного межбазового изменения.

Срок хранения каждой записи — сутки. Ошибка записи Redis журналируется, но уже прочитанные из PG профили остаются в текущем ответе. Автоматической инвалидации после изменения студента в PG нет.

## 12. Запрос №8. MongoDB: иерархия всех групп

Сначала:

```python
department_ids = sorted({group.department_id for group in groups.values()})
```

Это кафедры всех групп отчёта, в том числе групп без лекционных занятий за период.

```python
mongo_client[MONGO_DB]['university_hierarchy'].find(
    {'institutes.departments.department_id': {
        '$in': department_ids
    }},
    {'_id': 0, 'university_id': 1, 'name': 1, 'institutes': 1},
)
```

### Что возвращается

Документы вузов с `university_id`, `name` и полным вложенным массивом `institutes`. Служебный `_id` исключён.

Фильтр проверяет наличие нужной кафедры внутри документа. Он не сокращает массивы до одной кафедры. Python проходит институты и кафедры и формирует:

```python
hierarchy[department_id] = {
    'department_name': ...,
    'institute_id': ...,
    'institute_name': ...,
    'university_id': ...,
    'university_name': ...,
}
```

Все пять полей должны быть непустыми для каждой кафедры группы. Иначе — 503. Затем они присваиваются соответствующему `GroupInfoDTO`.

Даже если весь период пуст, группы и их иерархия остаются частью ответа, поэтому этот find всё равно выполняется при непустом списке групп.

## 13. Расчёт часов и сборка результата

Для каждой группы берутся её отсортированные студенты и её отобранные курсы.

```python
planned_classes = len(schedules_by_group[group_id][course_id])
attended_classes = attendance.get((group_id, student_id, course_id), 0)
planned_hours = planned_classes * 2
attended_hours = attended_classes * 2
```

У всех студентов одной группы одинаковый план конкретного курса, потому что он задаётся расписанием группы. Поэтому атрибуты курса, `planned_classes` и `planned_hours` формируются один раз в общем `courses` группы. В `students[].attendance` находятся только `course_id`, `attended_classes` и `attended_hours`. Посещения индивидуальны; при отсутствии отметок подставляется ноль. Общие курсы сохраняются даже у группы без студентов, если у неё есть подходящее расписание.

Сборка выполняется в Python, без дополнительных запросов к БД в этих циклах.

### Не путать два вида часов

- `lecture_hours` — заданный учебный объём всего курса из PostgreSQL.
- `planned_hours` — часы реально выбранных занятий группы за указанный период.

Код не подставляет `lecture_hours` в расчёт плана и не обязан получить равенство этих величин.

### Форма ответа

```text
[
  {
    group: {данные группы, специальности и иерархии},
    period_start,
    period_end,
    academic_hours_per_lecture: 2,
    courses: [{атрибуты курса, planned_classes, planned_hours}],
    students: [
      {
        профиль студента,
        attendance: [{course_id, attended_classes, attended_hours}]
      }
    ]
  }
]
```

Это схема структуры, не пример реального JSON-ответа.

### Поля группы

```text
group_id, group_name, speciality_id, department_id,
enrollment_year, curator, speciality_name, speciality_code,
degree_level, duration,
department_name, institute_id, institute_name,
university_id, university_name
```

### Поля студента

```text
student_id, group_id, first_name, second_name,
email, phone, student_card_number, status, attendance
```

### Поля курса

```text
course_id, speciality_id, department_id, course_name, description,
semester, duration_hours, lecture_hours, practice_hours,
planned_classes, planned_hours
```

Поля индивидуальной записи `attendance`: `course_id, attended_classes, attended_hours`.

Порядок групп задан `ORDER BY g.id`, студентов — сортировкой UUID, курсов — SQL-сортировкой `semester, name, id`.

## 14. Сколько обращений приходится на весь отчёт

При наличии групп, студентов и подходящих курсов:

| Операция | Прогретый кэш | Есть промахи |
|---|---|---|
| SQL групп | 1 | 1 |
| Cypher всех групп | 1 | 1 |
| SQL курсов | 1 | 1 |
| SQL посещений | 1 | 1 |
| Redis MGET всех студентов | 1 | 1 |
| SQL недостающих профилей | 0 | 1 |
| Redis pipeline записи | 0 | 1 вызов execute, с командой на каждый новый профиль |
| MongoDB find всех кафедр | 1 | 1 |

Итого PostgreSQL: три SQL при полном попадании кэша, максимум четыре при промахах. Это **не на одну группу**, а на весь запрос.

SQL групп, курсов и посещений выполняются на одном PG-подключении после Neo4j. Промахи профилей используют ещё одно подключение. Поэтому в полном сценарии одно подключение при прогретом кэше и два при промахах; SQL-запросов по-прежнему три и четыре. Ускорение по времени не измерялось.

Neo4j driver и MongoClient создаются в обработчике и закрываются контекстными менеджерами. Redis client существует на уровне модуля. Долгоживущего пула PG здесь нет.

В таблице считаются прикладные вызовы. Протокольные обмены, открытие соединений и возможные MongoDB getMore не являются отдельными строками алгоритма, но влияют на реальное время.

## 15. Ранние выходы и пустые данные

| Условие | Что произойдёт |
|---|---|
| Neo4j не нашёл группы | Без фильтра — `[]`, с названием — 404; остальные БД не вызываются |
| Для группы Neo4j нет данных в PG | 503, а не пропуск группы |
| У группы нет студентов | Группа в ответе, `students=[]` |
| У группы нет лекций в периоде | У группы `courses=[]`, студенты остаются с `attendance=[]` |
| Нет кандидатов курсов | SQL курсов и посещений пропускаются |
| Кандидаты есть, но ни один курс не подходит своей кафедре | У группы пустой `courses`, у студентов пустой `attendance`; SQL посещений не нужен |
| У студента нет присутствий | Курсы остаются, посещённые занятия и часы равны нулю |
| Во всём отчёте нет студентов | Redis MGET и SQL профилей не нужны |
| Redis недоступен | Все нужные профили читаются из PG |
| Для промаха не нашёлся профиль нужной группы в PG | 503 |
| Не найдена обязательная иерархия MongoDB | 503 |

Проверки пустых данных не превращают ошибку согласованности в успешный неполный отчёт. При этом полноценной проверки всех межбазовых инвариантов на каждом чтении нет: часть предположений остаётся на загрузке данных и отдельной сверке.

## 16. Почему это пакетная выборка

- Neo4j первым запросом формирует область групп, состав и расписание.
- UUID найденных групп передаются в PG одним массивом, без отдельного запроса каждой группы.
- Кандидаты курсов и промахи профилей передаются массивами точных пар.
- Посещения передаются массивами точных троек.
- Один MGET обслуживает всех студентов; один find обслуживает кафедры всех групп.
- Циклы построения словарей, распределения курсов по группам и формирования DTO работают с уже полученными данными.

Поэтому число запросов к БД не растёт линейно с числом групп. При этом сами массивы, ответы и объём обработки растут; пакетность не делает стоимость отчёта постоянной и не доказывает минимально возможное время на любом размере данных.

## 17. Ошибки и пределы реализации

- Ошибка подключения PG, недоступный Neo4j/MongoDB и явно обнаруженные рассогласования преобразуются в 503.
- Не всякая SQL-ошибка обёрнута в HTTPException. Ошибка исполнения запроса или сериализации может закончиться 500.
- Gateway сохраняет статус ошибки сервиса, но оборачивает его текст в своё поле `detail`. Сетевые ошибки прокси и его тайм-аут дают 503.
- Нет отдельного фильтра по студенту, году набора или семестру. В отчёт входят группы из Neo4j с учётом необязательного `group_name` и их лекционные курсы своей кафедры за период.
- Нет пагинации групп и студентов. На большом наборе ответ может быть объёмным.
- Проверка кэша сильнее, чем в первой лабе, но кэш всё ещё может содержать устаревшие значения до истечения срока.
- Общего согласованного снимка PG, Neo4j, Redis и MongoDB нет. Во время undo/заполнения отчёты могут возвращать ошибки или неполную область данных.
- JWT проверяется шлюзом. Собственной JWT-проверки у прямого порта `lab3.py` нет; сетевой запрет обхода должен обеспечиваться отдельно.
