# Лабораторная работа №1: поиск лекций и отчёт о посещаемости

Разбор текущего обработчика [`get_attendance_report`](../../Labs/lab1.py) и его прокси в [`gateway.py`](../../Labs/gateway.py). Ниже описано то, что делает код, а не предполагаемая «идеальная» реализация. SQL и Cypher приведены без изменения логики.

## 1. Что получает пользователь

Лаба находит лекции по тексту их материалов, определяет группы, которым они назначены за период, и выводит студентов с наименьшей посещаемостью этих занятий. По умолчанию — до десяти студентов.

Одна и та же лекция может проводиться несколько раз. Поэтому `lecture_id` обозначает учебный материал/тему занятия, а `schedule_id` — конкретное проведение занятия для группы. Посещаемость считается по `schedule_id`, а не по количеству найденных материалов.

Путь данных:

```text
Gateway: JWT и параметры
  → Elasticsearch: подходящие lecture_id
  → Neo4j: группы, студенты и назначенные занятия
  → PostgreSQL: число посещений
  → Python: процент, сортировка, limit
  → PostgreSQL: атрибуты итоговых групп
  → Redis: профили итоговых студентов
      → при промахах PostgreSQL → Redis
  → MongoDB: кафедры, институты и вузы
  → JSON-ответ
```

Запросы выполняются последовательно, не параллельно. Redis хранит профили, а не готовый отчёт.

## 2. Входной HTTP-запрос и Gateway

```http
GET /api/v1/labs/lab1/attendance-report?term=Базы%20данных&period_start=2026-09-01&period_end=2026-12-31&limit=10
Authorization: Bearer <JWT>
```

| Параметр | Значение по умолчанию в Gateway | Смысл |
|---|---|---|
| `term` | `Базы данных` | Текст для поиска в материалах |
| `period_start` | `2026-09-01` | Начало периода включительно |
| `period_end` | `2026-09-30` | Конец периода включительно |
| `min_attendance_pct` | `0.0` | Нижняя граница процента |
| `max_attendance_pct` | `100.0` | Верхняя граница процента |
| `limit` | `10` | Максимальное число студентов в ответе |

Период до декабря в примере указан явно. Это не значение по умолчанию: без параметров шлюз запрашивает только сентябрь.

Шлюз проверяет JWT через `jwt.decode(..., algorithms=['HS256'])`, включая срок действия `exp`, если он присутствует в токене. Штатный вход `POST /api/v1/auth/login` сравнивает логин и пароль с настройками окружения и выдаёт токен с `sub`, `role='analyst'` и сроком 12 часов. Отдельного запроса к БД при входе нет; отдельной проверки роли для отчётного метода также нет.

Прокси отправляет HTTP GET в `LAB1_URL`, по умолчанию `http://lab1-service:8001`, на тот же API-путь. Он передаёт заголовок `Authorization` и параметры, дополненные значениями по умолчанию. К БД сам Gateway не обращается. Тайм-аут HTTP-клиента — 30 секунд; это ограничение запроса к сервису, а не отдельный лимит каждого SQL-запроса.

Сам сервис требует `term` и обе даты; значения `example` в его Swagger не являются значениями по умолчанию. Он проверяет:

- даты должны разбираться как `date`;
- проценты находятся в диапазоне 0–100;
- `limit` находится в диапазоне 1–100;
- начало периода не позже конца;
- нижняя граница процента не больше верхней.

Ошибки типов и диапазонов дают 422. Перепутанные границы дают 400 до чтения хранилищ.

## 3. Запрос №1. Elasticsearch: поиск материалов

Индекс: `course_materials`.

Тело запроса ниже показано для фразы из примера. В коде вместо строки используется переменная `term`:

```json
{
  "query": {
    "multi_match": {
      "query": "Базы данных",
      "fields": ["title^3", "content_text"]
    }
  },
  "_source": ["lecture_id"]
}
```

Параметр вызова `es.search`: `size=10000`.

### Что происходит

- Elasticsearch ищет по названию материала `title` и его тексту `content_text`.
- `title^3` повышает вес совпадения в названии. Это влияет на релевантность материалов, но не на итоговый порядок студентов.
- `multi_match` — полнотекстовый поиск с анализом текста. Это не запрос `match_phrase`: точная последовательность всех слов не требуется. Оператор AND явно не задан.
- В `_source` возвращается только `lecture_id`. Тексты материалов в приложение не загружаются.

Обработчик читает `hits.hits`, берёт `hit['_source']['lecture_id']`, удаляет повторы через множество и сортирует UUID:

```python
lecture_ids = sorted({hit['_source']['lecture_id'] for hit in hits})
```

Несколько материалов одной лекции дают один UUID лекции.

### Что передаётся дальше

Только `lecture_ids` и исходные границы периода. Сведения о студентах на этом этапе ещё не нужны.

Если UUID нет, возвращается объект отчёта с `matching_lectures_count=0` и `students=[]`. Neo4j, PostgreSQL, Redis и MongoDB не вызываются.

### Ограничение

10 000 — предел документов материалов, а не уникальных лекций. Пагинации нет. При большем числе совпадений отчёт строится только по попавшим в выдачу материалам. Сам счётчик `matching_lectures_count` позже рассчитывается не по числу этих документов.

## 4. Запрос №2. Neo4j: группы, студенты и расписание

```cypher
MATCH (l:Lecture)<-[:FOR_LECTURE]-(sc:Schedule)<-[:HAS_SCHEDULE]-(g:Group)
WHERE sc.date >= $p_start AND sc.date <= $p_end
  AND l.id IN $lecture_ids
  AND l.type = 'Lecture'
WITH g, collect(DISTINCT sc.id) AS schedule_ids,
     collect(DISTINCT l.id) AS lecture_ids
MATCH (st:Student)-[:BELONGS_TO]->(g)
RETURN g.id AS group_id, schedule_ids, lecture_ids,
       collect(DISTINCT st.id) AS student_ids
```

### Входные параметры

| Параметр Cypher | Откуда взят |
|---|---|
| `$lecture_ids` | Уникальные UUID из Elasticsearch |
| `$p_start` | `str(period_start)` |
| `$p_end` | `str(period_end)` |

Даты хранятся в свойствах `Schedule.date` строками формата `YYYY-MM-DD`. При таком формате строковый порядок соответствует календарному; неправильный формат хранимого свойства нарушил бы это предположение.

### Чтение цепочки связей

```text
Group ─HAS_SCHEDULE→ Schedule ─FOR_LECTURE→ Lecture
Student ─BELONGS_TO→ Group
```

1. Найти лекции, чей `l.id` есть в списке Elasticsearch.
2. Оставить `l.type = 'Lecture'`. Практики и лабораторные могут иметь материалы в поисковом индексе, но здесь отсекаются.
3. Оставить конкретные занятия расписания за период, включая обе даты.
4. Определить связанные с ними группы.
5. Для каждой группы собрать уникальные `sc.id` и `l.id`.
6. Найти студентов группы и вернуть одну строку на группу.

### Возвращаемые поля

| Поле | Смысл |
|---|---|
| `group_id` | UUID группы с подходящими занятиями |
| `schedule_ids` | Уникальные конкретные занятия этой группы |
| `lecture_ids` | Уникальные темы/лекции этих занятий |
| `student_ids` | Уникальные UUID студентов группы |

`WITH g, collect(...)` выполняется до обхода студентов. Поэтому одинаковый список занятий не передаётся отдельно для каждого студента. `collect(DISTINCT st.id)` также убирает повторяющиеся UUID студентов.

Здесь используется обязательный `MATCH` студентов. Группа без студентов в результате отсутствует.

### Что делает Python после графа

Собираются:

```python
student_schedules[student_id] = {
    'group_id': group_id,
    'schedule_ids': schedule_ids,
}
```

Студенты одной группы ссылаются на общий объект её области занятий. Этот объект дальше не меняется.

Отдельно объединяются UUID лекций всех возвращённых групп в `scheduled_lecture_ids`. Именно размер этого множества станет `matching_lectures_count`: считаются подходящие лекции с расписанием в периоде и студентами в выбранных группах.

Если студентов в графовой выборке нет, обработчик возвращает пустой список студентов и не обращается к PostgreSQL, Redis и MongoDB.

**Важно:** в этом запросе нет проверки кафедры или специальности курса относительно группы. Это не фильтр «курсы своей кафедры» из третьей лабы. Принадлежность занятия группе определяется графовой связью `HAS_SCHEDULE`.

## 5. Запрос №3. PostgreSQL: агрегат посещений

Сначала формируются два общих списка:

- `student_ids` — все студенты графовой выборки;
- `schedule_ids` — объединение уникальных занятий всех этих групп.

```sql
SELECT a.student_id, COUNT(DISTINCT a.schedule_id) AS attended_classes
FROM attendance a
JOIN schedule sc ON sc.id = a.schedule_id
JOIN students st ON st.id = a.student_id AND st.group_id = sc.group_id
WHERE a.schedule_id = ANY(%s::uuid[])
  AND a.student_id = ANY(%s::uuid[])
  AND a.date BETWEEN %s AND %s
  AND a.mark = 1
GROUP BY a.student_id;
```

### Параметры psycopg2 по порядку

```python
(schedule_ids, student_ids, period_start, period_end)
```

`ANY(%s::uuid[])` проверяет принадлежность UUID переданному массиву. Значения передаются драйверу отдельно от SQL, а не вставляются в текст строковой конкатенацией.

### Условия и соединения

- `a.schedule_id = ANY(...)` ограничивает отметки нужными занятиями.
- `a.student_id = ANY(...)` ограничивает их нужными студентами.
- `a.date BETWEEN ...` проверяет дату отметки и позволяет PostgreSQL учитывать диапазон партиций `attendance` при построении плана. Конкретный способ доступа зависит от плана.
- `a.mark = 1` оставляет присутствия. Нули не считаются посещениями.
- Соединение с `schedule` даёт группу конкретного занятия.
- Соединение с `students` требует, чтобы группа студента совпала с группой этого занятия в PostgreSQL. Это важно, потому что входные массивы объединены по нескольким группам.

### Что возвращается

| Поле | Смысл |
|---|---|
| `student_id` | UUID студента |
| `attended_classes` | Число уникальных посещённых занятий из выбранного расписания |

`COUNT(DISTINCT a.schedule_id)` не даёт нескольким отметкам одного занятия увеличить результат. Студенты без присутствий не возвращаются SQL-агрегатом; Python позже подставляет им ноль через `attendance_stats.get(student_id, 0)`.

Имена, телефоны и названия групп этот запрос не читает.

## 6. Расчёт и отбор в Python — без запроса в БД

Для каждого студента:

```python
total_classes = len(student_schedules[student_id]['schedule_ids'])
attended_classes = attendance_stats.get(student_id, 0)
pct = round(attended_classes / total_classes * 100, 2)
```

Знаменатель — занятия подходящих лекций, назначенные группе за период. Это не все занятия курса и не все найденные текстовые материалы. При нулевом знаменателе студент пропускается.

Фильтр по проценту включительный:

```python
min_attendance_pct <= pct <= max_attendance_pct
```

Он применяется к уже округлённому значению. Сортировка:

1. меньший `attendance_percentage` выше;
2. при равенстве большее `total_classes` выше;
3. затем UUID студента по возрастанию для устойчивого порядка.

После сортировки берётся `[:limit]`. Если список пуст, дальнейшее чтение атрибутов и профилей прекращается.

Это ключевая граница: сведения для оформления отчёта читаются только после определения итоговых студентов.

## 7. Запрос №4. PostgreSQL: данные итоговых групп

`result_group_ids` — отсортированные уникальные `group_id` из уже ограниченного списка студентов.

```sql
SELECT
    g.id AS group_id,
    g.department_id,
    g.name AS group_name,
    sp.name AS speciality_name,
    sp.code AS speciality_code,
    sp.degree_level
FROM groups g
JOIN specialities sp ON sp.id = g.speciality_id
WHERE g.id = ANY(%s::uuid[]);
```

Параметры:

```python
(result_group_ids,)
```

### Возвращаемые поля

- `group_id` — UUID группы, по нему результат соединяется со статистикой из графа;
- `department_id` — UUID кафедры для последующего MongoDB find;
- `group_name` — название группы;
- `speciality_name` — название специальности;
- `speciality_code` — её код;
- `degree_level` — уровень образования.

`JOIN specialities` — обычный внутренний JOIN по `g.speciality_id`. Таблиц кафедр, институтов и вузов здесь нет.

Набор `group_rows` позже превращается в словарь `groups_by_id`. Группа ответа определяется статистикой из Neo4j и этой строкой PG, а не `group_id` из кэшированного профиля студента.

## 8. Запрос №5. Redis: профили итоговых студентов

```python
top_student_ids = [item['student_id'] for item in ranked_students]
cached_profiles = redis_client.mget(top_student_ids)
```

Команда протокола по смыслу:

```text
MGET <UUID студента 1> <UUID студента 2> ...
```

Ключ — UUID без префикса. Значение — JSON-строка. Порядок значений MGET соответствует порядку запрошенных ключей; `None` означает отсутствующий ключ.

Код принимает кэш, если удалось разобрать JSON, получен словарь и в нём есть:

```text
group_id, first_name, second_name, email, phone,
student_card_number, status
```

Неразбираемый JSON или неполный объект считаются промахом. Ошибки чтения Redis подавляются, и профили запрашиваются из PostgreSQL.

Проверка здесь слабее, чем в третьей лабе: не сверяется `profile['student_id']` с ключом и не требуется совпадение `profile['group_id']` с графом. Для финальной принадлежности к группе используется граф, однако остальные поля профиля могут оставаться устаревшими до истечения срока кэша. Наличие ключей также не является полной проверкой типов и содержимого значений.

## 9. Условный запрос №6. PostgreSQL: недостающие профили

Выполняется только при наличии `missing_student_ids`:

```sql
SELECT id AS student_id, group_id, first_name, second_name,
       email, phone, student_card_number, status
FROM students
WHERE id = ANY(%s::uuid[]);
```

Параметры:

```python
(missing_student_ids,)
```

Возвращаются UUID студента и группы, имя, фамилия, почта, телефон, номер студенческого и статус. Все промахи читаются одним SQL-запросом, а не запросом на каждого человека. UUID преобразуются в строки для JSON и ключей Redis.

Этот SQL не содержит фильтра группы. Принадлежность для отчёта уже определена предыдущими этапами.

Если нужной строки студента в PG не оказалось, эта лаба не выдаёт отдельную 503 из-за неполного состава: при окончательной сборке студент без профиля будет пропущен. Новый студент взамен не добирается, поэтому ответ может оказаться короче `limit`.

## 10. Условные записи №7. Redis: заполнение кэша

Для каждого прочитанного из PostgreSQL профиля:

```python
redis_client.setex(
    student_id,
    86400,
    json.dumps(profile, ensure_ascii=False),
)
```

По смыслу:

```text
SETEX <UUID студента> 86400 <JSON профиля>
```

Запись хранится сутки. В первой лабе `SETEX` вызывается отдельно для каждого промаха; pipeline здесь нет. Ошибка записи кэша подавляется: уже прочитанный профиль остаётся доступным для текущего ответа.

Автоматической инвалидации при изменении студента в PostgreSQL нет.

## 11. Запрос №8. MongoDB: иерархия итоговых групп

`target_department_ids` берутся из `department_id` строк `group_rows`.

```python
mongo_client[MONGO_DB]['university_hierarchy'].find(
    {'institutes.departments.department_id': {
        '$in': list(target_department_ids)
    }},
    {'_id': 0, 'name': 1, 'institutes': 1},
)
```

### Фильтр

Выбирает документы университетов, внутри которых есть хотя бы одна нужная кафедра. MongoDB — единственный источник цепочки университет → институт → кафедра.

### Проекция

- `_id: 0` исключает служебный идентификатор MongoDB;
- `name: 1` возвращает название вуза;
- `institutes: 1` возвращает вложенные институты **целиком**, вместе с их кафедрами.

Фильтр по вложенному `department_id` не обрезает содержимое возвращённого массива. Python проходит массивы и оставляет нужные кафедры.

Для каждой кафедры формируется:

```python
department_hierarchy[department_id] = {
    'department_name': department['name'],
    'institute_name': institute['name'],
    'university_name': university['name'],
}
```

Нужная кафедра должна присутствовать, и все три названия должны быть заполнены. Иначе 503. К одному документу вуза могут относиться несколько итоговых групп, но отдельный find на каждую группу не выполняется.

## 12. Сборка ответа

Сопоставляются три независимых набора:

1. `ranked_students`: UUID, группа, число занятий, число посещений, процент;
2. `student_profiles`: личные сведения из Redis/PG;
3. `groups_by_id` и `department_hierarchy`: группа, специальность и названия подразделений.

Верхний уровень:

```text
term, period_start, period_end,
min_attendance_pct, max_attendance_pct,
matching_lectures_count, students[]
```

У каждого студента:

```text
student_id, first_name, second_name, email, phone,
student_card_number, status,
group_name, speciality_name, speciality_code, degree_level,
department_name, institute_name, university_name,
total_classes, attended_classes, attendance_percentage
```

`limit` не возвращается отдельным полем верхнего уровня.

## 13. Сколько обращений выполняется

Речь о вызовах прикладного кода; установка соединения, служебные команды драйвера и MongoDB getMore сюда не включены.

| Сценарий | Вызовы |
|---|---|
| Нет совпадений ES | Один `search` |
| ES нашёл материалы, граф не дал студентов | `search` + один Cypher |
| Никто не прошёл диапазон посещаемости | ES + Neo4j + SQL посещений |
| Непустой ответ, профили в кэше | ES + Neo4j + два SQL + MGET + MongoDB find |
| Непустой ответ, есть промахи | То же + один SQL профилей + по одному SETEX на прочитанный профиль |

Два обычных SQL выполняются на двух свежих PG-подключениях. При промахах добавляется третье. Neo4j driver и Redis client созданы на уровне модуля; у Neo4j задан пул до 50 соединений. Это не означает, что PostgreSQL тоже использует пул: `get_pg_conn()` каждый раз вызывает `psycopg2.connect()`.

## 14. Ошибки и ограничения

- Ошибки ES, Neo4j и MongoDB в соответствующих блоках превращаются в 503. Ошибка подключения PG также превращается в 503.
- Ошибки выполнения SQL и последующей обработки не везде перехватываются. Нельзя считать, что любая ошибка любой БД обязательно вернётся как 503.
- Список занятий и принадлежность к группе приходят из Neo4j, а посещения и часть проверок группы — из PG. UUID и даты между хранилищами должны совпадать; общей межбазовой транзакции отчёта нет.
- Рейтинг строится по отобранным занятиям периода, не по учебному плану курса в целом.
- Сетевой доступ напрямую к порту сервиса не защищается этим JWT-прокси: собственная JWT-проверка в `lab1.py` отсутствует. Это отдельный вопрос конфигурации сети.
- Файл описывает запросы по исходникам. Новые обращения к живым БД и новый тестовый прогон для этой Markdown-документации не выполнялись.
